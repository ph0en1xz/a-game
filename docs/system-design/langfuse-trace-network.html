The order is not arbitrary. Nothing in the new half of this diagram can reach anything until the policy pass lands, and every miss presents as a crashloop or a refused connection rather than a policy error. So the sequence is web → worker → one policy pass → callback flip, and the bootstrap Job's real run waits for the same gate.

What you deploy, what you already have

option C — reuse the app's stateful workloads

reuseda-game-postgresTransactional side: your login, the org, the project, and the API keys LiteLLM authenticates with. A new langfuse database inside the existing StatefulSet — not a second pod.
reuseda-game-redisIngestion queue on logical db 1, beside the app's cache on db 0. This is what stops Redis being removable.
one-shota-game-create-lang-dbA Job, not a script. Creates the langfuse role and database inside the existing Postgres, then deletes itself. Idempotent — re-running only rotates the role's password.
newlangfuse-webTwo jobs in one pod: the ingestion API that LiteLLM posts to, and the UI you read traces in. Also the only container that runs headless init.
newlangfuse-workerDrains the queue and does the writing. Nothing ever connects to it.
newClickHouseTraces, observations, scores. Columnar, append-heavy, built for "p95 latency by model this week". Postgres cannot substitute for it.
newMinIORaw event bodies as blobs. Stands in for S3 the way LocalStack stands in for AWS.

Why the database arrives as a Job. A Job is a pod, so it reaches Postgres exactly the way api, brain and worker already do — over the network, with a Secret. An exec script would rely on the local socket's passwordless auth inside a-game-postgres-0, and neither the socket nor that pod exists once Postgres is RDS. On EKS only PGHOST changes.

  • Six ports total, and only one of them is new to your cluster: 3000, 3030, 8123, 9000 arrive with Langfuse; 5432 and 6379 you already allow, they just gain new clients — three more on 5432 once the Job is counted.
  • ClickHouse needs two ports open, not one. 8123 is HTTP for queries, 9000 is the native TCP protocol used by CLICKHOUSE_MIGRATION_URL. Open only 8123 and everything looks fine until the migration runs.
  • langfuse-worker needs no ingress policy at all. Nothing connects to it — it only ever dials out. Same reasoning your file already records for brain and worker: unreachable by default is correct, not an omission.
  • DNS is already handled. a-game-network-egress-policy is podSelector: {} and opens 53 to kube-dns in kube-system, so every new pod inherits name resolution. It also inherits the default-deny that blocks everything else.

What a missing rule looks like. The bootstrap Job's first real run is the worked example: the container started cleanly, then failed in about a second, five times, and the Job controller deleted the pod on BackoffLimitExceeded — taking the logs with it before ttlSecondsAfterFinished ever mattered. A one-second failure is a refused connection, not a timeout; k3s enforces policy in-process and rejects rather than drops. Two habits follow: while debugging a Job, use restartPolicy: Never with backoffLimit: 0 so the failed pod and its logs survive, and read kubectl describe job when no pod appears at all — a missing ServiceAccount never reaches the logs.

Why the browser needs no policy. kubectl port-forward is not pod-to-pod traffic. It tunnels through the API server to the kubelet, which opens the connection to the pod from the node's network namespace — so there is no source pod for a podSelector to match, and the ingress rules never come into play. That's also why it's the cheap way in: no Traefik rule, no host-based Ingress, no NEXTAUTH_URL carrying port 8080. The moment you swap it for a real Ingress, all three come back.

Which secret feeds which edge

six secrets — and only two of them are new values

SecretHoldsRead byHow it's wired
db-credentialsPostgres superuser — POSTGRES_USER, POSTGRES_PASSWORDthe bootstrap Job, and nothing else in LangfuseExplicit secretKeyRef renaming both to PGUSER / PGPASSWORD
lang-db-credentialsthe langfuse role's password — PGPASSWORDJob, web, workerJob reads it as LANG_PG_PASSWORD; web and worker as DATABASE_PASSWORD
clickhouse-credentialsCLICKHOUSE_USER, CLICKHOUSE_PASSWORDClickHouse itself, web, workerenvFrom — the image and Langfuse read the same two variable names
minio-credentialsMINIO_ROOT_USER, MINIO_ROOT_PASSWORDMinIO itself, web, workerFour secretKeyRef entries — the names don't match, so envFrom is wrong here
langfuse-credentialsSALT, ENCRYPTION_KEYweb and worker, byte-identicalenvFrom on both containers
langfuse-web-secretsNEXTAUTH_SECRET + six LANGFUSE_INIT_*web onlyenvFrom on web
  • Reference, don't copy. ClickHouse's and MinIO's credentials are read straight from the secrets those datastores already own. A copied credential is a credential that can drift — rotate MinIO's password and Langfuse follows on restart instead of silently failing uploads.
  • No DATABASE_URL. Langfuse accepts DATABASE_HOST, DATABASE_NAME, DATABASE_USERNAME and DATABASE_PASSWORD instead, so the password is read from one key rather than embedded in a connection string that has to be kept in lockstep with it. Set one form or the other, never both.
  • The three-way split is forced by SALT and ENCRYPTION_KEY. They must be byte-identical across web and worker, which is why they can't live in the web-only secret — and the six LANGFUSE_INIT_* keys must not reach the worker, which is why they can't live in the shared one. ENCRYPTION_KEY is hex-32; SALT and NEXTAUTH_SECRET are base64-32.
  • The superuser password stops at the Job. Nothing in the running system holds it — that's the argument against an initContainer on langfuse-web, which would have mounted it into an application pod that stays up.

Two things to verify before the policy pass. If clickhouse-credentials also carries a CLICKHOUSE_DB key, envFrom injects it into Langfuse — and Langfuse needs default. That variable is what cost the first ClickHouse boot: a-game in an unquoted CREATE DATABASE parses the hyphen as minus and exits with a syntax error. Second, Langfuse runs its schema migrations as CLICKHOUSE_USER; if that's a restricted user rather than default, the migration is where you'll find out.

What changes on EKS

the local shortcuts, and which ones carry forward

  • Postgres becomes RDS and only PGHOST moves. The Job is a pod reaching a network endpoint with a Secret, which is the same shape either way. db-credentials survives as a Secret object, synced from AWS Secrets Manager by External Secrets — not the CSI driver alone, since secretRef needs a real Secret.
  • MinIO becomes S3. Which also retires the least-privilege compromise here: Langfuse currently authenticates as MinIO root, acceptable for a single-tenant local store, replaced by a scoped credential on EKS.
  • NetworkPolicy stops being enforced unless you make it. EKS ignores every policy in 50-networkpolicies.yaml without the VPC CNI policy agent or Calico — silently, with everything still working. The CIDRs in that file are k3d and flannel; on EKS pods carry real VPC addresses.
  • kubectl port-forward stops being the way in. A real Ingress brings back the Traefik-equivalent rule, the host name, and a NEXTAUTH_URL that has to match what the browser actually types.
