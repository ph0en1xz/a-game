IRSA: how one pod gets its own IAM role

Without this, every pod on a node shares the node role's permissions. IRSA swaps a Kubernetes identity for an AWS identity, per pod, with no stored keys.

The exchange, at a glance

token travelling trust being verified ordinary call

Set up once, by Terraform

The OIDC provider

Your EKS cluster signs identity tokens from its own issuer URL. aws_iam_openid_connect_provider registers that issuer in IAM, so AWS is willing to believe tokens it signed.

The role's trust policy

An IAM role allows sts:AssumeRoleWithWebIdentity from that provider — conditioned on one exact namespace:serviceaccount. This is what stops any other pod using the role.

What happens at runtime

1

You → Kubernetes

The ServiceAccount names a role

You annotate the pod's ServiceAccount with eks.amazonaws.com/role-arn. That annotation is the entire link between the Kubernetes world and the AWS world.

2

Admission webhook → Pod

A signed token is projected into the pod

As the pod is admitted, EKS mutates it: a short-lived JWT signed by the cluster's OIDC issuer is mounted at a file path, and AWS_ROLE_ARN plus AWS_WEB_IDENTITY_TOKEN_FILE are set as environment variables.

The token's audience is sts.amazonaws.com and its subject is system:serviceaccount:<namespace>:<name> — the claim the trust policy checks.

3

Pod → AWS STS

The SDK trades the token for credentials

The AWS SDK inside your container finds those two environment variables on its own and calls sts:AssumeRoleWithWebIdentity, presenting the JWT. You write no credential code.

4

AWS STS → OIDC issuer

STS verifies the signature

STS fetches the issuer's public keys over the internet and checks the JWT was genuinely signed by your cluster, then checks the audience and that the subject matches the role's trust condition.

5

AWS STS → Pod

Temporary credentials come back

Valid for about an hour, refreshed automatically by the SDK before they expire. Nothing long-lived is ever stored in the cluster.

6

Pod → AWS service

The pod calls AWS as itself

Secrets Manager, S3, whatever the role allows — and only that role, not the node's.

Why it matters here. The node role is attached to the EC2 instance, so every pod scheduled on it inherits the same access. If one pod needs to read the Anthropic API key, all of them can.

Three certificates, easily confused

WhichWhere it comes fromWhat it proves
cluster_ca_data Private CA that EKS generates for the cluster That cluster_endpoint really is your API server — the kubectl/Helm handshake
issuer TLS cert A public CA (Amazon Trust Services) That the OIDC issuer URL is genuine. Its root fingerprint is the thumbprint_list the tls_certificate data source reads
signing keys (JWKS) The cluster's OIDC issuer That a pod's token was signed by your cluster — what STS checks at step 4

The ADR 0008 claim. "Only the gateway holds the Anthropic credential" is enforced by exactly two things: this IRSA trust condition on the IAM side, and the egress NetworkPolicy on the Kubernetes side. Neither alone is sufficient.

IRSA has no local equivalent — service-account annotations are inert on k3s and only take effect against real EKS (ADR 0009).
