How the public ALB reaches your pods

The load balancer lives in the public subnets and forwards to API pods running on EKS nodes in the private subnets. Inbound traffic comes down the orange path; the pods reach the internet back out through the NAT gateway.

The inbound request, step by step

  1. 1A client resolves api.a-game.dev to the ALB and opens an HTTPS connection on :443.
  2. 2Traffic enters the VPC through the Internet Gateway and hits the ALB interface in a public subnet.
  3. 3The ALB terminates TLS, checks its target group for a healthy pod, and load-balances across AZs.
  4. 4It forwards the request to an api pod on an EKS node in a private subnet, on :8000 — the pod itself is never exposed to the internet.
  1. ↩Egress: when a pod calls out (e.g. football-data.org), its route table sends 0.0.0.0/0 to the NAT Gateway, which fronts the request with a public IP. Nothing on the internet can start a connection back in.

The subnet tags are placement hints for the LB Controller. role/elb = "internet-facing ALBs land here"; role/internal-elb reserves the private tier for an internal LB you may never create.
Two subnets per tier, one per AZ, so a single AZ failure doesn't take the API down — the ALB just routes to pods in the surviving zone.
On LocalStack the ALB and NAT are mocked — they show up in state but don't route real traffic. This all comes alive only against real AWS + EKS.
