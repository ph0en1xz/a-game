How a change in Git reaches a pod

  1. 1You push to main on github.com/ph0en1xz/a-game. Nothing in the cluster has noticed yet.
  2. 2repo-server clones the repo over :443 — the one component with internet egress — renders the manifests, and caches the result in redis on :6379.
  3. 3application-controller asks repo-server for that rendered state on :8081, and asks the API server on :6443 what is actually running.
  4. 4If they differ, the controller writes the desired state to the API server. It never opens a connection to an a-game pod — that is why no cross-namespace policy exists between argocd and a-game.
  5. 5The kubelet on the node acts on the API server's new state and starts, stops or replaces the pod.

How a request reaches the API

  1. 1A request arrives at traefik in kube-system, which holds :8080 on the node.
  2. 2The a-game-api Ingress routes it to the a-game-api Service on :80, which resolves to a pod IP in 10.42.0.0/16.
  3. 3The pod's own NetworkPolicy has to allow ingress from kube-system, or the request is dropped after routing succeeds — a failure that looks like a broken app, not a broken policy.

a-gameThe application and everything it stores or measures.
kube-apiserverNot a pod. Reached at the node address on 6443.

The API server is not a pod, and policy knows it. The kubernetes Service on 10.43.0.1:443 is rewritten by kube-proxy to 172.18.0.2:6443 before NetworkPolicy is evaluated. A rule written against the Service never matches — it has to be an ipBlock of the node address. Confirm it with kubectl get endpoints kubernetes after any cluster rebuild, because k3d reassigns Docker addresses in start order.

Argo CD never touches an application pod. Everything it does to a-game goes through the API server, so there is no argocd → a-game flow to allow. The absence of that rule is correct, not an oversight.

Port-forward does not arrive from a pod. It comes through the API server to the kubelet, which opens the connection from the node. Tighten ingress on argocd-server without allowing the node address and the UI goes dark with no obvious cause. Upstream leaves that policy open for exactly this reason.

Two pods reach the internet, and only those two. The ingestion worker calls the sports data API; litellm calls Anthropic. Both are ipBlock: 0.0.0.0/0 on :443, which is as narrow as an egress rule to a third-party API can be without pinning addresses that change.

Single replica everywhere, one node, no HA. A deliberate choice at this stage — the topology is for learning the objects, not for surviving failure.
