## Components Flow Description
This section outlines the three most critical operational flows implemented within the application:
## Flow A: Client (Postman/Browser) $\rightarrow$ API Service $\rightarrow$ Redis Cache
The API service exposes three GET endpoints and one POST endpoint. Additionally, it hosts a WebSocket server that subscribes to Redis channels and listens for real-time events.

* POST /auth: Used for authentication. Returns a token required for all subsequent API endpoints and for authenticating WebSocket connections.
* GET /leagues: Fetches the complete list of supported football leagues directly from the PostgreSQL database.
* GET /league/{{league_name}}: Fetches upcoming fixtures for a specific league (e.g., /league/premier_league) from PostgreSQL.
* GET /predictions/{{team}}: Retrieves data for a specific team (e.g., /predictions/chelsea) by executing the following logic:
1. Checks if the requested prediction data exists in the Redis cache.
   2. If found, returns the data immediately.
   3. If missing, returns a REQUEST_PENDING status.
   4. Publishes an asynchronous message event to the RabbitMQ server to trigger calculation.

Note: The client must wait a few seconds and poll the exact same /predictions/{{team}} endpoint to fetch the generated result once it is saved to Redis. In a future phase (Phase 2), the Next.js browser app will eliminate this polling by subscribing to the WebSocket server to listen for completion events.
## Flow B: Calculation/AI Service $\rightarrow$ Claude API (Haiku)
The Calculation service subscribes to the specific RabbitMQ topic designated for incoming team-related requests. When it consumes an event indicating a prediction is missing from Redis, it performs the following steps to generate it:

* Connects to PostgreSQL using the database driver to fetch relevant historical metrics populated by the Ingestion Worker.
* Uses this raw data to execute the core algorithm that processes the required football statistics.
* Calls the Claude API (Haiku model) to generate natural, human-readable commentary summarizing the statistics.
* Connects to the self-hosted Redis service to cache the final output with a Time-To-Live (TTL) value of 6 hours.

By saving the output to Redis, the Pub/Sub mechanism triggers automatically. The WebSocket server inside the API service receives this event, allowing it to stream the update to connected clients (relevant for the Phase 2 Next.js application).
## Flow C: Ingestion Worker $\rightarrow$ External Sports API (football-data.org)
This service is triggered by a cron scheduler every 6 hours. Its primary responsibility is data synchronization:

* Fetches raw sports data from the external football-data.org free-tier API.
* Executes data cleaning, transformation, and enrichment pipelines.
* Saves the sanitized data to the PostgreSQL database.
